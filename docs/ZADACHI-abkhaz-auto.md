# `djonua/abkhaz-auto` — задачи на `/api/sto/*` для приложения автосервиса

Приложение «АбхазАвто Бизнес» (`djonua/abkhaz-sto`, `business.abkhaz-auto.ru`)
написано целиком: экраны, серверные действия и клиентский слой
`src/lib/api/*`. Половина экранов мертва, потому что маршрутов `/api/sto/*` на
сайте нет. Ниже — список задач на сайт: по одной на маршрут или на связную
группу маршрутов, с проверяемым Definition of Done.

Источник контракта — `abkhaz-sto/docs/API-sushchnosti.md`; типы ответов в
задачах взяты дословно из `abkhaz-sto/src/lib/api/*.ts` и менять их нельзя:
это TypeScript, который уже собран в приложении.

**Всего задач: 31**, плюс раздел 9 — дыры в самом контракте, которые надо
закрыть решением, а не кодом.

---

## Общее для всех задач (читать один раз)

### Аутентификация

Ed25519 service-ticket в заголовке `x-service-ticket` (`@zebrooo/service-ticket`),
как у promo-bff. Приложение подписывает `STO_TICKET_PRIVATE_KEY`
(`src = abkhaz-sto`, `dst = abkhaz-auto`), сайт проверяет
`STO_TICKET_PUBLIC_KEY`, допустимые `src` — из `STO_ALLOWED_SRC`.

Тикет подтверждает, что запрос пришёл **из приложения**, а не **кто** его
сделал. Поэтому в каждом вызове есть `shopId` и `actorUserId`, и сайт обязан
проверить оба:

1. сервис принадлежит `actorUserId` — по `shops.user_id` или подтверждённому
   телефону учётки (`shop-owner.ts`), ровно как в `booking-event`;
2. роль `actorUserId` в этом сервисе позволяет то, что он просит.

Клиентская проверка роли в приложении — подсказка интерфейсу, а не граница
доступа. Границу ставит сайт.

### Конверт ответа

| Исход | Тело | Статус |
|---|---|---|
| удача | `{ "data": … }` | 200 |
| подпись не принята | `{ "error": { "code": "unauthorized", "message": "…" } }` | 401 |
| роль не та / чужой сервис | `{ "error": { "code": "forbidden", … } }` | 403 |
| сущности нет | `{ "error": { "code": "not_found", … } }` | 404 |
| кривые данные | `{ "error": { "code": "validation_error", … } }` | 400 |
| гонка правок | `{ "error": { "code": "conflict", … } }` | 409 |
| частят | `{ "error": { "code": "rate_limited", … } }` | 429 |
| упало | `{ "error": { "code": "internal", … } }` | 500 |

Коды — существующие строки из `abkhaz-auto/src/lib/api/errors.ts`. Приложение
понимает ровно их (`abkhaz-sto/src/lib/api/site-api.ts`); неизвестный код
схлопывается по статусу. Ответ 200 **без** ключа `data` приложение считает
поломкой сайта (`internal`), поэтому пустой список — это `{ "data": [] }`, а не
пустое тело.

**404 — нормальное состояние, а не ошибка.** У нового сервиса нет ни мастеров,
ни осмотров, ни заметок. Приложение такой ответ не логирует и рисует пустое
состояние раздела. Отдавать вместо «ещё не заводили» 500 или пустой 200 там,
где ожидается объект, нельзя: экран соврёт.

### Таймауты, время, телефоны

- Чтение — 3 с, запись — 8 с. Ответ дольше = для экрана недоступность сайта.
- Время везде ISO-8601. Границы периодов (`from`, `to`) — по часам сервиса,
  Europe/Moscow фиксированным `+03:00`.
- Телефоны — E.164, тем же `normalizePhone`, что везде на сайте.

### Заготовка для проверок DoD

```bash
BASE=https://abkhaz-auto.apsoftgroup.ru      # тест-контур
TICKET=…   # x-service-ticket, выпущенный issueServiceTicket({src:"abkhaz-sto",dst:"abkhaz-auto"})
SHOP=…     # id одобренной витрины рубрики service
OWNER=…    # user_id владельца витрины
MASTER=…   # user_id сотрудника с ролью master
ALIEN=…    # user_id человека, не имеющего отношения к сервису

g() { curl -s -o /tmp/b -w '%{http_code}\n' -H "x-service-ticket: $TICKET" "$BASE/api/sto/$1"; cat /tmp/b; echo; }
p() { curl -s -o /tmp/b -w '%{http_code}\n' -H "x-service-ticket: $TICKET" -H 'content-type: application/json' -d "$2" "$BASE/api/sto/$1"; cat /tmp/b; echo; }
```

Каждая задача считается принятой, когда её чек-лист DoD проходит целиком на
тест-контуре и на экране приложения видно описанное в пункте «что видно в
приложении».

### Общий DoD, обязательный для каждой задачи ниже

- [ ] Запрос без `x-service-ticket` или с чужой подписью — `401 unauthorized`.
- [ ] `actorUserId`, не имеющий отношения к `shopId`, — `403 forbidden`
      (не 404 и не пустой список).
- [ ] Ответ всегда в конверте `{ data }` / `{ error: { code, message } }`,
      `content-type: application/json`.
- [ ] Отсутствующий или нечисловой обязательный параметр — `400 validation_error`
      с человеческим `message` (его показывают на экране как есть).
- [ ] Чтение укладывается в 3 с, запись — в 8 с на данных боевого размера.
- [ ] Маршрут не кэшируется (приложение ходит с `cache: "no-store"`, сайт
      обязан отвечать свежим).

# Раздел 0. Каркас

## Задача 1. Каркас `/api/sto/*`: подпись, конверт, роль по `actorUserId`

**Зачем.** Без него не работает ни один экран приложения: каждый вызов
`src/lib/api/*` идёт через один и тот же путь проверки. Сегодня приложение
получает `not_configured`/`unavailable` и показывает «Сайт сейчас недоступен»
на всех разделах — «Доступы», «Мастера», «Осмотр», «Отчёты», «Сводка», «Чат».

**Маршруты.** Собственных нет: это общий слой (middleware/хелпер) под все
остальные задачи.

Состав:

1. `verifyServiceTicket` — проверка `x-service-ticket`, `src` из
   `STO_ALLOWED_SRC`, `dst = abkhaz-auto`; отказ — `401 unauthorized`.
2. `resolveActor(shopId, actorUserId)` → `{ role: "master"|"admin"|"owner" } | null`:
   владелец витрины (по `shops.user_id` или подтверждённому телефону учётки,
   как `shop-owner.ts`) — всегда `owner`; иначе строка сотрудника; уволенный
   (`active = false`) и посторонний — `null` → `403 forbidden`.
3. Витрина обязана быть `status = approved` и рубрики `service`; иначе
   `403 forbidden`.
4. Конверт `{ data }` / `{ error: { code, message } }` поверх существующего
   `src/lib/api/errors.ts`.
5. Таблица сотрудников (миграция): `sto_members (shop_id, user_id null, phone,
   role, master_id null, active, added_at, invited_by)`, уникальность
   `(shop_id, user_id)` и `(shop_id, phone)`.

**Права.** Слой сам прав не даёт — он их вычисляет. Роль `owner` не хранится
строкой и не отзывается: тот, чья витрина, всегда хозяин.

**Поведение в углах.**
- Подписи нет, просрочена, чужой `src` — `401 unauthorized`.
- `shopId` не существует / не `approved` / не `service` — `403 forbidden`.
- `actorUserId` не сотрудник и не владелец — `403 forbidden`.
- `actorUserId` — уволенный сотрудник (`active = false`) — `403 forbidden`
  (не сужение прав до мастера: приложение читает записи с телефонами клиентов
  напрямую, и «мастер без поста» видел бы их все).

**DoD.**
- [ ] Миграция `sto_members` применена на тест-контуре, откат проверен.
- [ ] `g "members?shopId=$SHOP&actorUserId=$OWNER"` → 200 (маршрут из задачи 3).
- [ ] Тот же запрос без заголовка — 401, код `unauthorized`.
- [ ] Тот же запрос с `actorUserId=$ALIEN` — 403, код `forbidden`.
- [ ] Витрина в статусе `pending` — 403 на любом `/api/sto/*`.
- [ ] Юнит-тест `resolveActor`: владелец по `user_id`, владелец по телефону,
      админ, мастер, уволенный, посторонний — шесть случаев.
- [ ] В приложении: раздел «Доступы» перестаёт показывать «Связь с сайтом не
      настроена».

**Зависимости.** Нет. Блокирует все остальные задачи.

# Раздел 1. Люди и роли — без них мастера и админы не входят в приложение

## Задача 2. `GET /members/mine` — витрины, где человек работает

**Зачем.** Единственный вызов **без `shopId`**: приложение только входит и ещё
не знает сервиса. Владелец находит витрину по владению, а мастер и админ
витрины не имеют — сегодня они упираются в экран «Сервис не найден» и в
приложение не попадают вовсе. Оживляет вход любого сотрудника и роль в шапке.

**Маршруты.**

| Метод | Путь | Параметры | Ответ |
|---|---|---|---|
| GET | `/api/sto/members/mine` | `actorUserId` | `MyShopMembership[]` |

```ts
type MyShopMembership = {
  shopId: number;
  role: "master" | "admin" | "owner";
  masterId: number | null;
  /** Выключенный сотрудник входит, но ничего не видит. */
  active: boolean;
};
```

**Права.** Любому вошедшему — про себя. `actorUserId` здесь и есть предмет
запроса; отдавать чужой список нельзя ни при каких условиях.

**Поведение в углах.**
- Человек нигде не сотрудник — `{ "data": [] }`, 200. Не 404.
- Витрины `status != approved` или рубрики не `service` в ответ не попадают
  (приложение это перепроверяет, но фильтрует сайт).
- Владельца витрины в ответе нет: его роль не хранится строкой, приложение
  находит её само по владению.
- Уволенный сотрудник приходит с `active: false` — приложение не пускает его
  в сервис вовсе.

**DoD.**
- [ ] `g "members/mine?actorUserId=$MASTER"` → 200, массив со `shopId` его
      сервиса, `role: "master"`, `active: true`.
- [ ] `g "members/mine?actorUserId=$ALIEN"` → 200 `{"data":[]}`.
- [ ] `g "members/mine"` без `actorUserId` → 400 `validation_error`.
- [ ] Витрину перевели в `pending` — её `shopId` пропал из ответа.
- [ ] Сотруднику выключили доступ — в ответе `active: false`, `shopId` на месте.
- [ ] В приложении: мастер, приглашённый по SMS, входит на
      `business.abkhaz-auto.ru` и видит «Мой пост» (`/moi-raboty`), а не
      «Сервис не найден»; в шапке подпись роли «Мастер».

**Зависимости.** Задача 1.

## Задача 3. `GET /members` — список сотрудников сервиса

**Зачем.** Экран «Доступы» (`/dostupy`) у хозяина: список людей с ролями и
переключателями. Сегодня там только он сам, собранный из контекста.

**Маршруты.**

| Метод | Путь | Параметры | Ответ |
|---|---|---|---|
| GET | `/api/sto/members` | `shopId`, `actorUserId` | `StoMember[]` |

```ts
type StoMember = {
  userId: string;            // учётка на сайте — она же ключ строки
  name: string;
  phone: string | null;
  role: "master" | "admin" | "owner";
  masterId: number | null;   // строка мастера, если человек ещё и на посту
  active: boolean;           // выключенный входит, но ничего не видит
  canRemove: boolean;        // у владельца — false
  addedAt: string;
};
```

**Права.** Только `owner`. `master` и `admin` — `403 forbidden`.

**Поведение в углах.**
- **Владелец обязан быть первой строкой** с `role: "owner"`, `canRemove: false`
  и настоящим именем и телефоном учётки. Иначе сервис можно оставить без
  хозяина: приложение рисует переключатели всем, у кого `role != "owner"`.
- Сотрудников нет — в ответе одна строка владельца, а не `[]` и не 404.
- Приглашённый, ещё не вошедший, в списке есть: `userId` — идентификатор
  приглашения, `name` — то, что ввёл хозяин, `active: true`.

**DoD.**
- [ ] `g "members?shopId=$SHOP&actorUserId=$OWNER"` → 200, первая строка —
      владелец, `canRemove: false`.
- [ ] Тот же вызов с `actorUserId=$MASTER` → 403 `forbidden`.
- [ ] У сервиса без сотрудников ответ — ровно одна строка (владелец).
- [ ] `phone` приходит в E.164 (`+7940…`), приложение форматирует его само.
- [ ] В приложении: `/dostupy` показывает всех, у владельца бейдж «владелец»
      без переключателей, у остальных — сегмент «Мастер / Админ» и тумблер.

**Зависимости.** Задачи 1, 2.

## Задача 4. `POST /members/invite` — приглашение сотрудника по номеру (SMS)

**Зачем.** Кнопка «Пригласить по номеру» на `/dostupy` и ссылка «Пустить
мастера в приложение по номеру телефона» с экрана «Мастера». Это
единственный способ завести в сервисе кого-то, кроме владельца.

**Маршруты.**

| Метод | Путь | Тело | Ответ |
|---|---|---|---|
| POST | `/api/sto/members/invite` | `{ shopId, actorUserId, phone, role, name? }` | `InviteResult` |

```ts
type InviteResult = { userId: string | null; pending: boolean };
```

`role` — `"master"` или `"admin"`; `"owner"` приложение не шлёт и сайт не
принимает. `name` — до 80 символов, может отсутствовать.

**Права.** Только `owner`.

**Поведение в углах.**
- Учётки с таким номером ещё нет — сайт заводит приглашение на номер, отвечает
  `{ userId: null, pending: true }` и **отправляет SMS**; роль включается, когда
  человек войдёт этим номером на сайте.
- Учётка есть — `{ userId: "…", pending: false }`, человек появляется в
  `/members` и в своём `/members/mine` сразу.
- Номер уже сотрудник этого сервиса — `409 conflict` («этот человек уже
  работает в сервисе»), а не молчаливая перезапись роли.
- Номер не разбирается `normalizePhone` — `400 validation_error`.
- `role: "owner"` или неизвестная роль — `400 validation_error`.
- Номер владельца витрины — `400 validation_error` («он и так хозяин»).

**DoD.**
- [ ] `p members/invite '{"shopId":…,"actorUserId":"…","phone":"+79400000001","role":"master","name":"Ахра"}'`
      → 200 `{"data":{"userId":null,"pending":true}}`, на номер пришла SMS с
      приглашением.
- [ ] Тот же номер вторым вызовом → 409 `conflict`.
- [ ] Номер существующей учётки → 200, `pending: false`, и эта учётка сразу
      видна в `GET /members`.
- [ ] `"phone":"12"` → 400 `validation_error`.
- [ ] `"role":"owner"` → 400 `validation_error`.
- [ ] Вызов от `admin` → 403 `forbidden`.
- [ ] Номер нормализован: `8 940 000-00-01`, `+7 940 000 00 01` и
      `79400000001` дают одну и ту же строку сотрудника.
- [ ] Текст SMS согласован с владельцем площадки и содержит ссылку на вход.
- [ ] В приложении: после приглашения тост «Приглашение ушло по SMS — роль
      включится после входа», человек появился в списке `/dostupy`.

**Зависимости.** Задачи 1, 3.

## Задача 5. `POST /members/role` — сменить роль сотрудника

**Зачем.** Сегмент «Мастер / Админ» в строке сотрудника на `/dostupy`:
одно нажатие, без «Сохранить».

**Маршруты.**

| Метод | Путь | Тело | Ответ |
|---|---|---|---|
| POST | `/api/sto/members/role` | `{ shopId, actorUserId, userId, role }` | `StoMember` |

**Права.** Только `owner`.

**Поведение в углах.**
- `role: "owner"` — `400 validation_error`: владение передаёт поддержка
  площадки, а не этот маршрут.
- `userId` — сам владелец — `403 forbidden` (его роль не хранится строкой).
- `userId` не сотрудник этого сервиса — `404 not_found`.
- Ответ — **вся строка** `StoMember` после правки: экран рисует её из ответа.

**DoD.**
- [ ] `p members/role '{"shopId":…,"actorUserId":"$OWNER","userId":"…","role":"admin"}'`
      → 200, `data.role == "admin"`.
- [ ] Повторный тот же вызов → 200 и та же строка (идемпотентно, не 409).
- [ ] `"role":"owner"` → 400 `validation_error`.
- [ ] `userId` владельца → 403 `forbidden`.
- [ ] Незнакомый `userId` → 404 `not_found`.
- [ ] Вызов от `admin` → 403 `forbidden`.
- [ ] В приложении: нажатие «Админ» в строке даёт тост «Теперь админ», и у
      этого человека в его сессии открываются разделы админа.

**Зависимости.** Задачи 1, 3.

## Задача 6. `POST /members/active` — включить и выключить доступ

**Зачем.** Тумблер в строке сотрудника на `/dostupy`: увольнение без удаления
истории.

**Маршруты.**

| Метод | Путь | Тело | Ответ |
|---|---|---|---|
| POST | `/api/sto/members/active` | `{ shopId, actorUserId, userId, active }` | `StoMember` |

**Права.** Только `owner`.

**Поведение в углах.**
- `active: false` — человек перестаёт быть сотрудником для всех `/api/sto/*`:
  любой его вызов отвечает `403 forbidden`, а `GET /members/mine` отдаёт строку
  с `active: false`. Сужать права до мастера нельзя.
- Владельца выключить нельзя — `403 forbidden`.
- `userId` не сотрудник — `404 not_found`.
- Строка мастера (`masterId`) при выключении **не трогается**: уволить
  сотрудника и уволить мастера — разные решения (задача 9).

**DoD.**
- [ ] `p members/active '{"shopId":…,"actorUserId":"$OWNER","userId":"…","active":false}'`
      → 200, `data.active == false`.
- [ ] Сразу после этого любой вызов с этим `actorUserId` → 403 `forbidden`.
- [ ] `GET /members/mine` для него → 200, строка с `active: false`.
- [ ] Обратное включение возвращает прежнюю роль и прежний `masterId`.
- [ ] Выключить владельца → 403 `forbidden`.
- [ ] В приложении: выключенный сотрудник, обновив страницу, видит «Войдите на
      сайте» / «Сервис не найден» вместо разделов; в `/dostupy` его строка
      блёкнет и подписана «доступ выключен».

**Зависимости.** Задачи 1, 3.

# Раздел 2. Связь учётки со строкой мастера

## Задача 7. Привязка учётки к строке мастера (`masterId`)

**Зачем.** Сейчас `StoMember.masterId` в ответе есть, а поставить его нечем:
`/members/invite` принимает только телефон и роль, `POST /masters` — имя,
специальность и пост. Из-за этого `ctx.masterId` у всех `null`: приглашённый
мастер работает (отмечается на подъёмнике, ведёт осмотр, пишет отчёт), но в
отчёте остаётся без имени, привязки записей к нему не доходят, а «Отчёты за
смену» на `/moi-raboty` и фильтр `masterId` в `/otchety` показывают ему весь
сервис вместо своего.

**Маршруты.** Достаточно одного — какой сайту удобнее:

| Метод | Путь | Тело | Ответ |
|---|---|---|---|
| POST | `/api/sto/members/master` | `{ shopId, actorUserId, userId, masterId \| null }` | `StoMember` |
| или POST | `/api/sto/members/role` | то же тело, что и роль, плюс поле `masterId` | `StoMember` |

**Права.** Только `owner`.

**Поведение в углах.**
- Одна учётка — не больше одной строки мастера в сервисе, и наоборот: попытка

## Задача 9. `POST /masters/update` — правка мастера, смена, увольнение, `orphaned`

**Зачем.** Три сценария сразу: тумблер «на смене» на `/mastera`, шторка правки
(имя, специальность, пост), «Уволить»/«Вернуть в штат» и — главное — кнопка

**Маршруты.**

| Метод | Путь | Тело | Ответ |
|---|---|---|---|
| POST | `/api/sto/masters/update` | `{ shopId, actorUserId, masterId, name?, speciality?, postNo?, onShift?, active? }` | `MasterUpdate` |

```ts

```

Патч **строго частичный**: экран шлёт только изменённые поля. Поля, которых
нет в теле, трогать нельзя — иначе хозяин, поправивший опечатку в имени, молча

  «своя» = строка, чей `user_id` равен `actorUserId`. Чужую строку мастер не
  правит.
- `active` (уволить и вернуть) — **только `owner`**, при любой другой роли
  `403 forbidden`.

**Поведение в углах.**
- `onShift: false` или `active: false` **не трогают записи мастера**: они
  остаются на своих постах и ждут нового исполнителя. В ответе `orphaned` —
  номера записей, оставшихся без мастера (живые записи от «сейчас» и дальше).
- Нечего осиротить — `orphaned: []`.
- `masterId` чужого сервиса — `403 forbidden`; несуществующий — `404 not_found`.
- `postNo` больше числа постов — `400 validation_error`.
- Пустое тело патча — `400 validation_error` (приложение такого не шлёт).

**DoD.**

## Задача 15. `POST /inspections/photo-upload` — фото дефекта одноразовым адресом

**Зачем.** Мастер снимает дефект телефоном прямо в яме. Кнопка «Фото» в шторке
дефекта на `/zapis/[id]/osmotr` (компонент `PhotoUpload.tsx`). Без маршрута
кадры не отправляются вовсе, а отчёт клиенту уходит без картинок — то есть
неубедительным.

**Маршруты.**

| Метод | Путь | Тело | Ответ |
|---|---|---|---|
| POST | `/api/sto/inspections/photo-upload` | `{ shopId, actorUserId, contentType }` | `PhotoUpload` |

```ts
type PhotoUpload = { photoId: string; uploadUrl: string; expiresAt: string };
```

Файл идёт в хранилище **напрямую из браузера**: приложение делает
`fetch(uploadUrl, { method: "PUT", body: file, headers: { "content-type": … } })`,
а затем зовёт `POST /inspections/defects/update` с полным списком `photoIds`.
Перегон мегабайтов через контейнер приложения — только задержка.

**Права.** `master`, `admin`, `owner`.

**Поведение в углах.**
- `uploadUrl` живёт **не меньше пяти минут** (`expiresAt` — правдивый).
- `url` в ответе `Defect` — подписанный, живёт **не меньше часа**: экран
  отчёта и осмотра открывают его сразу.
- `contentType` — только `image/*`; приложение уже режет чужое до `image/jpeg`,
  сайт обязан отказать на `text/html` — `400 validation_error`.
- Хранилище обязано принимать `PUT` с заголовком `content-type` **с чужого
  origin** (`business.abkhaz-auto.ru`, на тесте
  `business.abkhaz-auto.apsoftgroup.ru`): без CORS-разрешения кадр не уйдёт, а
  приложение покажет «хранилище ответило 0».
- `photoId` — строка по маске `^[\w.-]{1,128}$`: приложение отбрасывает всё
  остальное молча, и кадр потеряется.
- Загруженный, но не привязанный к дефекту кадр должен убираться сборщиком
  мусора (мастер снял и передумал).

**DoD.**
- [ ] `p inspections/photo-upload '{"shopId":…,"actorUserId":"$MASTER","contentType":"image/jpeg"}'`
      → 200, `photoId` по маске `^[\w.-]{1,128}$`, `expiresAt` не раньше чем
      через 5 минут.
- [ ] `curl -X PUT -H 'content-type: image/jpeg' --data-binary @shot.jpg "$UPLOAD_URL"`
      → 2xx.
- [ ] Тот же `PUT` из браузера со страницы `business.abkhaz-auto.apsoftgroup.ru`
      проходит (проверка CORS: preflight `OPTIONS` отвечает `access-control-allow-origin`).
- [ ] `"contentType":"text/html"` → 400 `validation_error`.
- [ ] После привязки `photoIds` кадр приходит в `Defect.photos[].url`, ссылка
      открывается и живёт не меньше часа.
- [ ] Просроченный `uploadUrl` отвечает 4xx, а не молча 200.
- [ ] В приложении: мастер прикрепляет к дефекту до четырёх кадров подряд с
      телефона, каждый виден в шторке и в отчёте.

## Задача 21. `GET /garage` — машины клиента из его учётки

**Зачем.** Блок «Гараж клиента» в карточке `/klienty/[ключ]` и сверка машины в
`/mashiny/[ключ]`: «чем человек ездит сейчас». История ремонта по-прежнему

**Маршруты.**

|---|---|---|---|
| GET | `/api/sto/garage` | `shopId`, `actorUserId`, `clientUserId` **или** `phone` | `StoGarageCar[]` |

```ts

  id: number;          // vehicles.id сайта — он же ложится в sto_bookings.vehicle_id
  brand: string;
  model: string | null;
  year: number | null;
  plate: string | null;
  vin: string | null;
  primary?: boolean;   // машина, на которой человек ездит сейчас
};
```

**Права.** `admin`, `owner`.

```ts
};
```

Приложение ждёт ответа **2,5 секунды** (`site-events.ts`) и различает только

- [ ] Сообщение появляется в `GET /chat/messages` последним.
- [ ] `"text":"   "` → 400 `validation_error`.
- [ ] Заблокированный клиентом тред → 403 `forbidden` с внятным текстом.
- [ ] Чужой `threadId` → 403/404 по правилу выше.
- [ ] В приложении: форма ответа в `/chat/[id]` отправляет сообщение, оно
      появляется в переписке; ссылка «ответить на сайте» больше не нужна.

**Зависимости.** Задачи 1, 26.

# Раздел 9. Решённое хозяином — три задачи сверх двадцати восьми

Эти три дыры были вопросами к владельцу сервиса. Решения приняты 17.09.2026,
контракт (`docs/API-sushchnosti.md`) уже описывает маршруты, приложение уже
умеет их звать и показывает нужные состояния. Осталась сторона сайта.

## Задача 29. `POST /inspections/finish` — завершить осмотр

**Решение хозяина: отдельная кнопка.** Не «само закроется при отправке
отчёта».

**Зачем.** Кнопка «Завершить осмотр» на экране осмотра. Мастеру нужен момент,
после которого список дефектов застыл: отчёт клиенту уезжает ровно тот,
который он собрал.

| Метод | Путь | Тело | Ответ |
|---|---|---|---|
| POST | `/api/sto/inspections/finish` | `{ shopId, actorUserId, inspectionId }` | `Inspection` |

**Права.** `master`, `admin`, `owner`.

**Поведение в углах.**
- Идемпотентно: повтор отдаёт уже завершённый осмотр со `status: "finished"`,
  а не `409`. Кнопку жмут дважды с телефона в яме.
- `finishedAt` — момент завершения, он же «дата осмотра» в отчёте.
- После завершения `POST /inspections/defects`, `/defects/update`,
  `/defects/remove` и `/inspections/odometer` отвечают `409 conflict`.
- Отправка отчёта завершением не управляет и наоборот: `with_admin` и
  `with_client` живут своей жизнью.
- Чужой сервис — `403`, незнакомый `inspectionId` — `404`.

**DoD.**
- [ ] `p inspections/finish '{"shopId":…,"actorUserId":"$MASTER","inspectionId":…}'`
      → 200, `status: "finished"`, `finishedAt` — время вызова.
- [ ] Повтор того же вызова → 200 и тот же `finishedAt` (не обновился).
- [ ] `POST /inspections/defects` по завершённому осмотру → 409 `conflict`.
- [ ] `POST /inspections/odometer` по завершённому → 409 `conflict`.
- [ ] `GET /inspections` отдаёт `status: "finished"` и непустой `finishedAt`.
- [ ] Чужой сервис → 403, выдуманный id → 404.
- [ ] В приложении: кнопка «Завершить осмотр» закрывает осмотр и уводит в
      отчёт, «Снять дефект» и крестики у дефектов пропадают, шторка пробега
      становится читающей.

**Зависимости.** Задачи 1, 12, 13.

## Задача 30. `POST /inspections/odometer` — исправить пробег

**Решение хозяина: правку разрешаем** (пока осмотр не завершён).

**Зачем.** Поле пробега в шторке осмотра и кнопка «Исправить пробег». Цифру
вписывают на приёмке в спешке, а уезжает она клиенту в отчёт и в историю
машины.

| Метод | Путь | Тело | Ответ |
|---|---|---|---|
| POST | `/api/sto/inspections/odometer` | `{ shopId, actorUserId, inspectionId, odometerKm }` | `Inspection` |

**Права.** `master`, `admin`, `owner`.

**Поведение в углах.**
- Осмотр завершён — `409 conflict` (текст: «осмотр завершён, пробег не
  меняется»). Приложение в этом случае поле и не показывает.
- Пробег, уехавший назад по этой машине, — `400 validation_error`, тем же
  правилом, что и `/inspections/start`.
- Сайт пишет в историю осмотра, **кто и когда** поправил. Клиенту в отчёте —
  только итоговое число, без «было/стало».
- `odometerKm` не целое или ≤ 0 — `400 validation_error`.

**DoD.**
- [ ] `p inspections/odometer '{"shopId":…,"actorUserId":"$MASTER","inspectionId":…,"odometerKm":118000}'`
      → 200, `odometerKm: 118000`; `GET /inspections` отдаёт новое число.
- [ ] Значение меньше прошлого визита этой машины → 400 `validation_error`.
- [ ] По завершённому осмотру → 409 `conflict`.
- [ ] `"odometerKm":-5` и `"odometerKm":"много"` → 400 `validation_error`.
- [ ] В базе/логе видно, кто и когда поправил (покажите в PR, где это лежит).
- [ ] В приложении: шторка пробега открывается с текущим числом, «Исправить
      пробег» сохраняет, тост «Пробег исправлен: 118 000 км».

**Зависимости.** Задачи 1, 12, 29.

## Задача 31. `GET /reports/pdf` — «собирается, подождите»

**Решение хозяина: показываем «собирается».** Не держим соединение и не
готовим документ заранее.

**Зачем.** Кнопка «PDF» в отчёте. Документ со шрифтами и фотографиями
собирается дольше трёх секунд — столько приложение ждёт читающий вызов.

| Метод | Путь | Ответ |
|---|---|---|
| GET | `/api/sto/reports/pdf?shopId&actorUserId&inspectionId` | `{ url, expiresAt }` **либо** `{ ready: false, retryAfterMs? }` |

**Права.** `master`, `admin`, `owner`.

**Поведение в углах.**
- Документ ещё не собран — **немедленно** `{ ready: false, retryAfterMs }` (с
  кодом 200 или 202, приложение смотрит на тело). Соединение не держим:
  приложение оборвёт его на трёх секундах и покажет «Сайт сейчас недоступен».
- Собран — `{ url, expiresAt }`, ссылка живёт не меньше 10 минут.
- Повторный вызов во время сборки не запускает вторую сборку.
- Ошибка сборки — `500 internal` с человеческим текстом, а не вечное
  `ready: false`.

**DoD.**
- [ ] Первый вызов по свежему отчёту → ответ приходит быстрее секунды и
      содержит `ready: false`.
- [ ] Вызов через `retryAfterMs` → `{ url, expiresAt }`, ссылка открывается и
      отдаёт PDF с фотографиями дефектов.
- [ ] Десять вызовов подряд во время сборки не создают десять сборок
      (покажите в PR, чем это гарантировано).
- [ ] `expiresAt` не раньше чем через 10 минут после ответа.
- [ ] Чужой `inspectionId` → 403/404 по общему правилу.
- [ ] В приложении: по «PDF» появляется карточка «PDF собирается» с кнопкой
      «Проверить ещё раз», по ней документ открывается.

**Зависимости.** Задачи 1, 17, 20.

# Раздел 10. Чего всё ещё не хватает в контракте

## 10.1. Уволенные мастера в `GET /masters`

`Inspection.status` знает `finished` и `finishedAt`, но маршрута, который
переводит осмотр в это состояние, нет ни у сайта, ни в приложении. Кнопка
«Готово» на экране осмотра — просто переход к отчёту, и подпись у неё теперь
честная («Замечаний нет — к отчёту»).

Нужно решить: завершает ли осмотр отправка отчёта (`/reports/send`) — тогда
`finished` ставит сайт сам и отдельный маршрут не нужен, — или нужен
`POST /inspections/finish`. Пока не решено, `finished` в приложении не
появляется, а «правку дефекта запрещаем у завершённого осмотра» (задача 13)
проверить нечем.

## 10.1. Уволенные мастера в `GET /masters`

Приложение показывает уволенных отдельным списком и умеет вернуть человека в
штат — но это держится на том, что `GET /masters` отдаёт и `active: false`.
В контракте это не записано. Нужно зафиксировать: **отдаёт всех**, а
приложение делит список само (задача 8 это уже требует — осталось внести в
`docs/API-sushchnosti.md`).

## 10.2. Правка мастера админом

Сегодня в контракте всё, кроме `onShift`, правит только `owner`. Приложение
даёт админу менять имя, специальность и пост (увольнение оставили хозяину):
за стойкой опечатку исправляет он. Нужно либо разрешить это на сайте (задача
9), либо приложение вернёт админу запрет — и тогда кнопку надо убрать.

## 10.3. Кто такой «мастер» для записи, если он не в справочнике

Пока `/masters` молчит, `ctx.masterId` у всех `null`, и приложение живёт на
отметке подъёмника в куке устройства. Это осознанный запасной путь, но у него
есть цена: в отчётах нет имени мастера, а привязки записи к мастеру
(`/masters/assign`) не работают. Задачи 7 и 8 закрывают это — до них всё
остальное в разделе «Мастера» держится на честном слове.
