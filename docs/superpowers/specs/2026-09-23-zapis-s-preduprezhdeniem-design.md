# Запись с наложением и задним числом — через предупреждение

Дата: 2026-09-23. Статус: дизайн согласован.

## Зачем

Сервис живёт не по идеальному календарю: машину принимают задним числом,
две работы идут на одном посту, клиента берут «впритык». Сейчас приложение
жёстко отказывает: «Это время уже прошло», «Окно уже занято», «В это время
сервис не работает», а наложение на пост запрещает сама база. Нужно, чтобы
админ, хозяин или мастер могли записать вопреки этим правилам — осознанно,
через попап с предупреждением. Клиентский путь на сайте не меняется и
остаётся под всеми запретами.

## Объём

Четыре запрета превращаются в предупреждение с подтверждением:

| Причина  | Сейчас                                | Станет |
|----------|---------------------------------------|--------|
| `past`   | окно не предлагается в UI             | предупреждение «время уже прошло» |
| `taken`  | отказ формы + констрейнт базы (23P01) | предупреждение «накладывается на …» |
| `buffer` | отказ («впритык, нужен перерыв N мин»)| предупреждение |
| `closed` | отказ («вне часов приёма»)            | предупреждение |

Где работает: форма «Новая запись» (`/kalendar/novaya`), перенос списком
окон (`/kalendar?move=`), перетаскивание в сетке дня (`Timeline`) и в
неделе (`CalendarDrag`).

Что НЕ меняется: запись «с улицы» под осмотр (`createWalkInBooking`),
виджет записи на сайте, копия `src/lib/sto/slots.ts` (остаётся байт в байт
с сайтом), права ролей (force доступен всем, кому открыт раздел
`bookings`, — настоящую границу держит сайт).

## 1. Миграция в abkhaz-auto (отдельная задача и PR, идёт первой)

- `alter table public.sto_bookings add column overlap_ok boolean not null default false;`
- Констрейнт `sto_bookings_no_overlap` пересоздаётся:
  `exclude using gist (shop_id with =, post_no with =, tstzrange(starts_at, ends_at, '[)') with &&)
   where (status in ('new', 'confirmed') and not overlap_ok)`.

Смысл: запись, подтверждённая человеком через попап, помечается
`overlap_ok = true` и выпадает из констрейнта — её можно наложить, и на неё
можно наложиться. Обычные записи (сайт, запись без предупреждений)
по-прежнему сталкиваются друг с другом в базе — защита от гонки «два
клиента бронируют последнее окно» сохраняется. Код сайта не меняется:
он `overlap_ok` не ставит, default закрывает все его вставки.

## 2. Сервер приложения

### Новый чистый модуль `src/lib/slot-warnings.ts`

Своё, приложенческое — НЕ в `src/lib/sto/` (те файлы — копии сайта).

```ts
type SlotWarning = "past" | "closed" | "taken" | "buffer";
slotWarnings(input: {
  schedule; startsAt; durationMin; busy; postNo?; now;
}): { postNo: number; warnings: SlotWarning[]; conflicts: BusyInterval[] }
```

- `past` — `startsAt < now`, БЕЗ часа форы (`DEFAULT_LEAD_MIN` остаётся
  только фильтром свободных окон в UI; «через 30 минут» — не «прошло»).
- `closed` — выходной, разовый выходной или окно не целиком внутри
  интервала приёма (та же логика, что в `isSlotFree`).
- `taken` / `buffer` — пересечение с занятыми интервалами: жёсткое и
  только-по-буферу. `conflicts` — с кем пересеклись, для текста попапа.
- Выбор поста: задан → он и только он; не задан → первый свободный с
  буфером → первый свободный без буфера → пост с наименьшим числом
  пересекающихся записей (при равенстве — меньший номер).

### `src/lib/bookings.ts`

- `createManualBooking` и `rescheduleBooking` получают `force?: boolean`.
- Без `force` — поведение сегодняшнее (включая тексты ошибок).
- С `force`: `isSlotFree` не зовётся; пост и предупреждения даёт
  `slotWarnings`; в insert/update пишется
  `overlap_ok: warnings.includes("taken") || warnings.includes("buffer")`.
- Перенос БЕЗ предупреждений всегда пишет `overlap_ok: false` — запись,
  уехавшая из наложения в чистое окно, возвращается под защиту базы.
- Обработка 23P01 остаётся: гонка двух обычных записей всё ещё возможна.
- `overlap_ok` не читается и в `StoBookingRow` не добавляется (COLUMNS без
  него) — типы-копии сайта не трогаем.

### `src/app/(app)/actions.ts`

- `createManualAction` и `rescheduleAction` читают `force` из формы
  (кнопка `name="force" value="1"`).
- Без force: перед вызовом библиотеки действие само считает
  `slotWarnings`; есть предупреждения → возврат на экран с
  `warn=<причины через запятую>` (плюс контекст: для переноса —
  `bookingId`, `hhmm`, `postNo` едут в адресе, чтобы шторка подтверждения
  могла собрать свою форму). Набранное в форме едет назад по существующему
  механизму `typed`; к нему добавляется комментарий (`c=`) — сейчас он
  теряется при любом отказе, с попапом это стало бы массовым.
- С force: вызов библиотеки с `force: true`, дальше как обычно.

## 3. Попап

Стиль приложения — шторка `Sheet`, открытая параметром адреса; клиентское
состояние только там, где оно уже есть (перетаскивание).

- **Новая запись**: submit → сервер видит предупреждения → redirect с
  `?warn=` → поверх формы шторка «Записать всё равно?» с перечислением
  причин и записей, на которые накладываемся; в подвале — «Записать всё
  равно» (submit той же формы с `force=1`) и «Выбрать другое время»
  (ссылка, снимающая `warn`). Шторка рендерится внутри `<form>`, кнопка
  подтверждения — `<button name="force" value="1" type="submit">`.
- **Перенос списком окон**: тот же round-trip; шторка на `/kalendar` со
  своей маленькой формой (`bookingId`, `day`, `hhmm`, `postNo`, `force=1`
  из warn-параметров адреса).
- **Перетаскивание** (Timeline, CalendarDrag): бросок с причиной больше
  не отменяется молча. Компоненты клиентские и заранее знают конфликты
  (`dropAt`/`dayDropAt`), поэтому подтверждение показывается сразу на
  месте той же вёрсткой шторки: текст из `dropWarning`, «Перенести всё
  равно» отправляет скрытую форму с `force=1`, «Отмена» снимает состояние.
  Сервер при force не перепроверяет жёстко — гонка «пока смотрел попап,
  что-то изменилось» покрыта самим фактом подтверждения.

## 4. Выбор «плохого» времени в форме «Новая запись»

- Чипы окон показывают ВСЕ узлы сетки дня (шаг расписания по интервалам
  приёма), а не только свободные. Состояния чипа: свободно (как сейчас) и
  предупреждение (серый/штрих, `title` с причиной: занято / прошло /
  впритык). Выбор warn-чипа пишет причину в итоговую строку формы.
- Свободным считается окно из `freeSlots` (с форой часа, как сейчас);
  узлы между «сейчас» и «сейчас + фора» — обычные чипы без пометки
  «прошло»: сервер их и сегодня принимает.
- Полоса дней листается назад в прошлые даты, календарик (`DayPick`)
  пускает в прошлое (сейчас оба упираются в сегодня).
- Разовый выходной (`daysOff`): чипы строятся по часам этого дня недели,
  все с пометкой «выходной». День вообще без часов приёма (регулярный
  выходной) остаётся без чипов — формой туда не записать, только
  переносом. Принятое ограничение.

## 5. Сетка с наложениями

Наложившиеся живые блоки на одном посту рисовались бы друг поверх друга.
Минимальная правка Timeline и недельной сетки: блок, начинающийся внутри
другого, сдвигается лесенкой (левый отступ на глубину вложенности) и
рисуется поверх — оба видны и кликабельны. Новой раскладки нет; статистика
занятости может двоить минуты наложения — принято, вне объёма.

## 6. `src/lib/drag.ts`

- Добавляется причина `past`: `dropAt`/`dayDropAt` получают необязательную
  границу прошедшего (минута дня «сейчас» для сетки дня; для недельной —
  по дню), приоритет причин: overlap > buffer > closed > past.
- Тексты `dropWarning` дополняются («Время уже прошло — перенести задним
  числом?»); подпись под курсором остаётся красной, но бросок теперь
  ведёт к подтверждению, а не в никуда.

## 7. Тесты

- `slot-warnings.test.ts`: каждая из четырёх причин, их сочетания, выбор
  поста (заданный/свободный/без буфера/наименьшее пересечение), пустое и
  кривое расписание.
- `drag.test.ts`: причина `past`, приоритеты причин, бросок с конфликтом
  возвращает результат (а не блокируется).
- Тесты силовых путей `bookings`: `overlap_ok` ставится при taken/buffer,
  сбрасывается при переносе в чистое окно (уровень чистых функций —
  формирование патча/строки; сами запросы к базе не мокируются, как
  принято в репозитории).
